# Нативный интерфейс AI Assistant

Визуальная система, токены и UX-решения описаны в `docs/native_ui_design.md`.

Пункт **Extensions → AI Assistant → Open chat** открывает немодальное QML-окно внутри STE Slicer.
Браузер, `localhost` и веб-страница пользователю больше не показываются. HTTP-сервер продолжает работать
только ради `POST /mcp` для внешних MCP-клиентов.

## Структура окна

```
┌ Шапка ────────────────────────────────────────────────────────────┐
│ Проект «Кронштейн» · 4 сообщения     ● модель подключена   [⚙]    │
├ Полоса выполнения (на вкладках «Результат» и «Проекты») ─────────┤
│ ◌ Выполняю слайсинг · 85 %                          [Остановить]  │
├ Вкладки: Чат | Результат (счётчик изменений) | Проекты ───────────┤
│ Чат:       сообщения, одна карточка выполнения на запрос, ответы  │
│            поле ввода: вложения, «модель из сцены», режим, отправка│
│ Результат: состояние задачи, режим/материал/профиль, решения,     │
│            изменённые параметры (старое → новое), слайсинг,       │
│            время/расход/вес, G-code/3MF, папка, сброс, скриншот   │
│ Проекты:   список (имя, дата, число сообщений), создать, открыть, │
│            переименовать, удалить                                 │
└───────────────────────────────────────────────────────────────────┘
```

Отдельные окна: «Настройки подключения» (Base URL, модель, ключ, проверка подключения, папка результатов,
язык, подробность объяснений, автосохранение), подтверждения (новый проект с очисткой сцены, удаление проекта,
сброс изменений) и переименование проекта.

Макет структуры и состояний сделан локальным инструментом визуализации. Figma MCP в каталоге есть,
но не подключён (нужна авторизация аккаунта), поэтому не использовался. Внешний MCP — только инструмент
проектирования, в плагин он не попадает.

## Сценарии

1. **Первый запуск.** Не заданы Base URL, модель или ключ — вместо ленты показывается экран настройки:
   что нужно и зачем, кнопка «Открыть настройки». В настройках «Проверить подключение» отправляет короткий
   запрос с введёнными значениями и показывает понятный итог.
2. **Пустой проект.** Три шага (модель → требования → отправка) и шаблоны запросов.
3. **Модель из сцены.** Плагин сам видит объекты сцены (имя и габариты). Над полем ввода появляется
   «Использовать модель из сцены»; при нескольких объектах можно отметить нужные или взять всю сцену.
   Агенту передаётся служебная заметка с `object_id`, чтобы он не загружал модель повторно.
4. **Новые файлы.** STL, OBJ, 3MF, JPG, JPEG, PNG через нативный `FileDialog` или перетаскиванием (`DropArea`).
   Карточка вложения: превью изображения или значок формата, имя, размер, удаление до отправки.
   Формат и размер (до 100 МБ) проверяет Python; QML передаёт только `file://`-адрес, без base64.
5. **Запрос.** Enter — отправить, Shift+Enter — новая строка. Режим `Авто / 3D / 5D Spiral / 5D`, по умолчанию
   `Авто` (агент выбирает сам); остальные варианты фиксируют выбор пользователя через `forced_mode`.
   Во время работы отправка заблокирована, доступна «Остановить».
6. **Работа агента.** Одна карточка выполнения на запрос: этап, примерный процент, шкала, живой статус,
   свёрнутая история этапов; единственная кнопка «Остановить» остаётся в поле ввода. После завершения карточка становится итогом с показателями,
   «Посмотреть результат» и «Подробнее». Сырые аргументы и ответы — только в «Технических подробностях» этапа.
   Подробно — в разделе «Спокойная лента и модель запроса».
7. **Ошибки.** Карточка объясняет, что произошло, влияет ли это на результат и что делать. Кнопки по ситуации:
   «Повторить», «Открыть настройки», «Продолжить», «Продолжить без изображения», «Выбрать другой файл»,
   «Сбросить изменения». Демо-режима нет.
8. **Результат.** После слайсинга — итоговая карточка: режим, материал, профиль, время, длина и вес материала,
   основные изменения, кнопки сохранения G-code и 3MF, путь файла, «Открыть папку».
9. **Проекты.** Создание (с явным подтверждением очистки сцены и сброса настроек), открытие, переименование,
   удаление с подтверждением. Пока агент работает, переключение на другой проект запрещено, текущий
   проект можно просматривать.
10. **Закрытие и повторное открытие.** Закрытие окна только прячет его: агент продолжает работу, лента и прогресс
    восстанавливаются из той же модели. Окно стыкуется справа от слайсера (см. «Стыковка с окном слайсера»),
    закрытие стыкованного окна возвращает слайсеру прежнюю геометрию.

## Состояния окна

| Состояние | Что видно |
| --- | --- |
| `not_configured` | экран настройки вместо ленты, отправка недоступна |
| пустой проект | три шага и шаблоны |
| `idle` | лента, поле ввода активно |
| ожидание первого события | карточка с бегущей полоской и «Оцениваю задачу» |
| `running` | карточка выполнения: этап, ≈ %, живой статус; «Остановить» в поле ввода, на других вкладках — в полосе выполнения |
| `stopping` | «Останавливаю…», серая шкала, кнопка неактивна |
| отменено | «Остановлено» на достигнутом проценте и «Продолжить» |
| ошибка | карточка ошибки с действиями, поле ввода снова активно |
| слайсинг | реальный прогресс бэкенда в диапазоне 78–95 % карточки и на вкладке «Результат» |
| результат | итоговая карточка с экспортом |

Состояние подключения в шапке: «не настроено», «не проверено», «проверяю…», «подключено», «ошибка подключения».

## Связь QML и Python

```
QML (AssistantWindow.qml)  ──pyqtSlot──▶  NativeChatController (QObject, главный поток)
          ▲                                     │  читает EventBus каждые 150 мс (QTimer)
          │ pyqtProperty / notify, QAbstractListModel
          │                                     ▼
   ChatViewState (чистый Python) ◀── события агента ── EventBus ◀── Agent / MCP-инструменты (фоновые потоки)
```

- `ui/view_state.py` — чистая логика без Qt: превращает события шины в turns (сообщение, карточка выполнения,
  этапы, ответ), изменения параметров, решения, состояние слайсинга, итоги экспорта. Покрыта тестами.
- `ui/progress.py`, `ui/live_status.py`, `ui/markdown.py` — модель прогресса, живые статусы и безопасный разбор
  Markdown в блоки; без зависимостей от Qt.
- `ui/strings.py` — русские и английские строки интерфейса, названия инструментов, тексты ошибок.
- `ui/controller.py` — `QObject` с `pyqtProperty`/`pyqtSignal`/`pyqtSlot`, модели списков на базе
  `QAbstractListModel`. Все изменения моделей — в главном потоке: события читаются таймером главного потока,
  результаты фоновых задач возвращаются через сигнал с `Qt.QueuedConnection`.
- Длительные операции (LLM, инструменты, экспорт G-code/3MF, проверка подключения) идут в фоновых потоках.
  Сцена и настройки меняются инструментами через существующий `run_on_main`. Экспорт в главный поток не переносится.
- QML не делает HTTP-запросов, `XMLHttpRequest`, `fetch` и не опрашивает сервер. Это проверяется тестом.
- Шина событий получила счётчик `revision`: при `clear`/`load` (смена проекта) контроллер перестраивает ленту из снимка.

## Спокойная лента и модель запроса

Каждый запрос — отдельный turn. `ChatViewState` (`ui/view_state.py`) строит его поверх исходных событий
`EventBus`, которые по-прежнему сохраняются в проекте и служат для восстановления и диагностики:

```
Turn
├── сообщение пользователя                     элемент ленты kind=user
├── карточка выполнения                        элемент ленты kind=activity (обновляется на месте)
│   ├── progress / percent / indeterminate     ProgressTracker
│   ├── title — текущий этап                   «Настраиваю печать»
│   └── живой статус                           только в контроллере, не в модели ленты
├── stages — сгруппированные этапы             статус, итог одной строкой, факты, технические подробности
├── metrics, changes, decisions, exports       структурированные данные итога
├── короткий ответ ассистента                  kind=assistant: blocks (Markdown), plain, collapsible
└── ошибка, если нужна реакция                 kind=error
```

Лента не перестраивается целиком на каждое событие: `ChatViewState` выдаёт операции `append`/`update` только
для изменившегося элемента (повторные `update` одного элемента схлопываются), а `DictListModel.update`
отправляет `dataChanged` лишь с изменившимися ролями. Полный `reset` бывает только при смене проекта или языка.

### Модель прогресса (`ui/progress.py`)

Чистый Python-класс `ProgressTracker` без зависимостей от Qt. Процент — приблизительная оценка по фактически
наблюдаемым этапам, а не по времени: агент вызывает разное число инструментов, может пропускать этапы,
возвращаться к настройкам и повторять вызовы после ошибки.

| Этап | Инструменты | Диапазон |
| --- | --- | ---: |
| Подготовка | `get_changed_settings`, `reset_settings`, `get_machine`, `select_machine` | 0–8 % |
| Загрузка и сцена | `load_model`, `list_objects`, `delete_object`, `clear_scene` | 8–20 % |
| Анализ геометрии | `analyze_mesh`, `get_object_bounds` | 20–38 % |
| Рекомендации | `recommend_setup`, `list_materials`, `set_material`, `*_quality_profile`, `*_print_mode` | 38–55 % |
| Настройка печати | `get_setting`, `search_settings`, `set_setting(s)`, `create_profile` | 55–70 % |
| Ориентация | `suggest_orientation`, `set_orientation`, `lay_flat`, `align_symmetry_axis`, `rotate/move/scale_object`, `arrange_all` | 70–78 % |
| Слайсинг | `slice`, `get_slice_status`, `get_slice_result` + реальный прогресс бэкенда | 78–95 % |
| Экспорт | `export_gcode`, `save_project_3mf` | 95–98 % |
| Финальный ответ | итоговое сообщение ассистента | 98–100 % |

Правила:

- значение в рамках запроса только растёт (`max`), возврат к раннему этапу меняет подпись, но не процент;
- вход в этап поднимает значение до начала его диапазона — пропущенные этапы считаются пройденными;
- каждый завершённый вызов закрывает 45 % оставшейся части диапазона этапа (ошибка — половину шага),
  но не больше 85 % диапазона: повторы асимптотически приближаются к концу этапа и не дают скачка к 100 %;
- во время слайсинга реальная доля бэкенда `p` даёт `78 + 17·p` %;
- пока идёт работа, значение не выше 99 %; 100 % — только после события `done`;
- ошибка и отмена сохраняют достигнутый процент и меняют тон шкалы; повторное открытие окна или проекта
  проигрывает те же события и восстанавливает тот же процент;
- если ни одного распознанного этапа ещё не было, шкала неопределённая, подпись «Оцениваю задачу»;
- время до завершения не показывается: честно оценить его нельзя.

Ограничения оценки: процент отражает пройденные этапы, а не оставшееся время; долгий этап (например, ответ
LLM без инструментов или большой слайсинг) может держать процент на месте; если агент неожиданно вернётся
к слайсингу после экспорта, процент не уменьшится, но и не вырастет до повторного финала.

### Группировка инструментов

| Группа этапа | Инструменты | Итог |
| --- | --- | --- |
| модель | `load_model` | «Модель получена · bracket.stl» |
| геометрия | `analyze_mesh`, `get_object_bounds` | «Модель проанализирована · 62 × 40 × 35 мм» |
| рекомендации | `recommend_setup`, `set_material`, `set_quality_profile`, `set_print_mode`, `select_machine` | «Параметры печати подобраны · 3D · PETG · normal» |
| настройки | `set_setting`, `set_settings`, `create_profile` | «Настройки применены · Изменено параметров: 6» |
| сброс | `reset_settings` | «Настройки сброшены» |
| размещение | ориентация, поворот, перемещение, масштаб, `arrange_all` | «Модель подготовлена на столе» |
| слайсинг | `slice`, `get_slice_status`, `get_slice_result` | «Слайсинг завершён · 2 ч 14 мин · 46 г» |
| экспорт | `export_gcode`, `save_project_3mf` | «Результат сохранён · result.gcode» |

Подряд идущие вызовы одной группы объединяются в один этап. Служебные чтения (`get_setting`, `search_settings`,
`get_changed_settings`, `get_print_mode`, `get_machine`, `list_*`) не образуют самостоятельных этапов:
они попадают в подробности текущего или следующего этапа, а если кроме них ничего не было — в одну строку
«Контекст проверен». Ошибочный вызов виден внутри своего этапа; если следующий вызов той же группы успешен,
этап считается успешным с пометкой «Исправлено после ошибки», а текст ошибки остаётся в подробностях.
Промежуточные реплики модели рядом с вызовами тоже уходят в подробности этапа.

### Живые статусы

`ui/live_status.py` — локальные фразы по этапу, RU/EN, смена не чаще раза в 6–10 секунд, без повторов подряд,
редкий доброжелательный юмор, который прекращается при ошибке этапа; при ошибке, отмене и завершении строка
скрыта. Контроллер отдаёт её отдельным свойством `liveStatus`; в модель ленты, историю LLM, события шины и
проект она не попадает (это проверяется тестом). Настройка «Живые статусы» (`live_status`) включена по умолчанию.

### Финальный ответ агента

Системный prompt просит финальный ответ в 3–6 строк: результат, ключевые решения одной строкой, важное
предупреждение и предложение открыть «Подробнее». Таблицы параметров, время, расход и пути модель
не повторяет — их показывают структурированные компоненты. Текст рядом с вызовами инструментов — не длиннее
одного предложения. Предупреждения о безопасности не сокращаются. При включённых объяснениях добавляются
2–4 пункта с причинами ключевых решений.

## Язык интерфейса и модели

Единственный источник истины — `config.effective_language()`; им пользуются QML (через контроллер), лента,
живые статусы, подписи этапов, тексты ошибок, причины в `recommend_setup`, производные события, системный
prompt и названия новых проектов.

```
SettingsDialog → NativeChatController.saveSettings (проверяет auto/ru/en)
→ config.update_settings → Preferences (+ немедленный savePreferences)
→ config.effective_language → контроллер: languageChanged, перестройка ленты
→ prompts.system_prompt + заметка «Язык ответа» в сообщении пользователя → запрос к LLM
```

- Явно выбранный `Русский` или `English` всегда важнее языка STE Slicer.
- `Авто` учитывает язык STE Slicer, системную локаль и текст текущего запроса. Русская системная локаль
  не теряется, даже если старый STE Slicer работает на английском. Русский или английский текст запроса
  задаёт язык конкретного ответа; интерфейс использует язык окружения. Если ни один источник не распознан,
  используется английский (`FALLBACK_LANGUAGE`). В настройках показан текущий язык интерфейса.
- Неизвестное сохранённое значение считается `Авто`; в prompt больше не уходит «язык с кодом 'de'».
- Изменение применяется сразу: интерфейс перестраивается без перезапуска, следующий запрос строит prompt
  заново. Уже отправленные сообщения не переводятся.
- В конце системного prompt стоит отдельный строгий языковой контракт на выбранном или распознанном языке: все сообщения
  пользователю, включая приветствие, только на этом языке; английские результаты инструментов и сообщения
  слайсера пересказываются, без перевода остаются только файлы, пути, идентификаторы, материалы и устоявшиеся
  обозначения. Каждое сообщение пользователя дополнительно получает короткую служебную заметку «Язык ответа».
- Подписи настроек слайсера (`Wall Line Count` и т. п.) переводятся каталогом самого STE Slicer
  (`fdmprinter.def.json`, `ru_RU`) — и в ленте, и в результатах инструментов для модели.

## Названия проектов (`server/titles.py`)

Новый проект называется «Новый проект» / «New project» (показывается на текущем языке). Название
появляется, когда понятна задача, и после этого стабильно:

1. **Агент.** В тот же запрос, где модель начинает работу, ей доступен скрытый инструмент `set_project_title`
   (только пока проект ждёт названия). Его вызов обрабатывается внутри агента: в шину событий, ленту,
   карточку выполнения и ответ пользователю он не попадает, отдельного платного запроса нет. Название
   проходит очистку (2–6 слов, до 48 символов, без «Проект», путей и расширений, не приветствие).
2. **Детерминированный fallback.** Если агент название не дал, после завершения запроса оно строится из текста
   пользователя без LLM: отбрасываются приветствия и вежливые слова, служебные заметки, «подготовь/нужно
   напечатать», «для печати»; берётся первая содержательная фраза, винительный падеж приводится к
   именительному, добавляется материал («Кронштейн из PETG», «Шестерня редуктора», «PETG bracket»). Если в
   тексте нет предмета, используется имя модели без расширения и номеров версий (`bracket_final_v12.stl` →
   `Bracket`). Приветствия и «Продолжи выполнение задачи» название не меняют.
3. **Стабильность.** Поле `title_source`: `default` → `auto` (один раз) или `manual` (после переименования —
   навсегда). Старые проекты без поля открываются как раньше: бессодержательное старое имя вроде «Привет»
   считается стандартным и будет заменено, осмысленное — сохраняется.

## Стыковка с окном слайсера (`ui/dock.py`, `ui/dock_layout.py`)

В STE Slicer 7.10 (Cura 3.6) нет механизма dock- или side-панелей для плагинов: боковая панель слева
принадлежит активной стадии (`sidebarComponent`) и заменяет настройки печати, а главное окно — QML
`UM.MainWindow`, а не `QMainWindow` с `QDockWidget`. Встраивать элемент поверх рабочей области запрещено,
поэтому ассистент остаётся отдельным немодальным окном, а `DockManager` раскладывает два окна рядом:

- при открытии запоминает состояние главного окна (normal/maximized и нормальную геометрию), делает его
  обычным и занимает `availableGeometry` экрана, на котором стоит слайсер: слайсер — слева, ассистент —
  справа, около 25 % ширины, оба на всю доступную высоту (панель задач не перекрывается);
- окна стыкуются по видимым рамкам (на Windows — через DWM, с учётом невидимых рамок Windows 10/11),
  поэтому между ними нет щели и перекрытия при масштабах 100–200 %;
- ширина ассистента не меньше его минимальной (380 логических пикселей × масштаб), слайсеру остаётся не меньше
  половины экрана; на маленьких экранах ассистент никогда не занимает больше половины;
- перетаскивание общей границы меняет долю ассистента, она запоминается в `panel_share` (15–40 %);
- стыковка задаёт удобную стартовую раскладку, но не блокирует окна: если пользователь перемещает ассистент,
  слайсер сразу возвращается к исходной геометрии, а ассистент остаётся там, куда его перенесли; перемещение
  самого слайсера также не отменяется таймером;
- закрытие ассистента возвращает слайсеру прежние положение, размер и состояние; в настройках слайсера
  (`general/window_*`) всё время хранится исходная геометрия, поэтому ни обычное, ни аварийное завершение не
  оставляет её изменённой;
- старое `window_geometry` больше не используется: разумная ширина переводится в долю один раз, полноэкранная
  отбрасывается, поле очищается; ошибочно сохранённая доля в половину экрана сбрасывается к 25 %;
- окно не поверх всех окон: это обычное немодальное окно, привязанное к слайсеру (`transientParent`),
  повторное открытие показывает тот же экземпляр.

## Что из старой SPA

| Часть SPA | Судьба |
| --- | --- |
| `index.html`, `app.js`, `style.css`, `i18n.js` | помечены как legacy, из слайсера не открываются; удаление — отдельное решение |
| `/api/*` | сохранены для совместимости и существующих тестов, нативный UI их не использует |
| демо-режим | не переносится |
| переключатель темы | не переносится: окно следует теме слайсера |
| правая панель сцены | заменена блоком «модель из сцены» и вкладкой «Результат» |
| шаблоны ТЗ | перенесены на экран пустого проекта |
| `/mcp` | без изменений |

## Ограничения Qt/QML из состава слайсера

- Дистрибутив STE Slicer 7.10 собран с Qt 5.10 и Python 3.5. Импорты ограничены `QtQuick 2.2`,
  `QtQuick.Controls 1.1`, `QtQuick.Controls.Styles 1.1`, `QtQuick.Layouts 1.1`, `QtQuick.Dialogs 1.1`,
  `QtQuick.Window 2.2`, `UM 1.2`. Нет `StackLayout`, `Controls 2`, `BusyIndicator` из Controls 1.1, `TextArea.placeholderText`.
- Многострочный ввод — собственный `TextEdit` во `Flickable`: у `TextArea` из Controls 1 Enter перехватывается внутренним
  редактором, а обработчик `Keys` на самом `TextEdit` позволяет отличить Enter от Shift+Enter.
- В теме слайсера одна тема — `material` (светлая). Тёмной темы нет, поэтому окно берёт цвета из `UM.Theme` и
  автоматически подстроится, если тема появится.
- `DropArea` работает в Qt 5.10 для файлов из проводника; если перетаскивание не срабатывает, остаётся `FileDialog`.
- Скриншот сохраняет видимую часть окна (`QQuickWindow.grabWindow`), а не всю прокрученную ленту.

## Решение по legacy-интерфейсу

Папка `web/` и маршруты `/api/*` оставлены: на них опираются существующие тесты и внешние сценарии, а удаление
не даёт пользователю выигрыша. Из слайсера браузерный интерфейс больше не открывается (`webbrowser` удалён),
в документации он помечен как legacy. `/mcp` работает как прежде.

## Проверка

- Юнит-тесты: логика ленты, ошибки и действия, режимы, вложения, проекты, настройки, проверка подключения,
  отмена, повторное открытие, фоновый экспорт, отсутствие HTTP в нативном UI. `tests/test_native_progress.py`:
  монотонность и диапазоны прогресса, mapping и группировка инструментов, исправленные ошибки, 100 % только
  после `done`, реальный процент слайсинга, восстановление после повторного открытия, живые статусы вне истории
  LLM и проекта, сворачивание длинного текста без потери оригинала, структурированные изменения параметров,
  безопасный Markdown, обновление только изменившихся ролей модели.
- `scripts/check_qml.py` — импорты не новее Qt 5.10/Controls 1.1, запрет конструкций новых версий Qt и сетевых API.
- Загрузка окна в Qt 5.15 с заглушкой `UM` (тема из настоящего `theme.json` слайсера) без единого QML-предупреждения;
  `scripts/preview_native_ui.py` рендерит состояния окна в PNG для RU/EN и разных масштабов: ожидание,
  анализ, применение настроек с раскрытой историей, слайсинг 10/55/95 %, итог, раскрытые параметры,
  технические подробности, узкое окно, ошибка с частичной работой, остановка, отмена, длинный ответ
  свёрнутый и раскрытый, Markdown-таблица.
- Smoke-тест в STE Slicer 7.10.12 (Windows, масштаб 150 %): окно открывается из меню в одном экземпляре, без QML-ошибок
  в журнале; настройки, экран первого запуска, обнаружение модели из сцены, отправка с реальным агентом и понятная
  карточка сетевой ошибки проверены. Слайсинг, экспорт и повторное открытие в слайсере проверяет пользователь вручную.
- В тестовой среде дистрибутив запускается только с `MKL_DEBUG_CPU_TYPE=5`: встроенная Intel MKL не поддерживает
  процессор машины. Это ограничение дистрибутива, не плагина.
